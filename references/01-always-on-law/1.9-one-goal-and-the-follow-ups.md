# 1.9 [rule] One goal; what you find on the way is written down, never chased (long form)

> **Long form.** The binding text is the short form in `law/engineering-law.md`, which the
> user-global `CLAUDE.md` loads into every session. This file keeps the reasons and the full
> wording the short form compresses; read it when a rule needs its reasoning. If the two ever
> differ, the short form wins and this file is the defect.

**A task has exactly one main goal, and it ends when that goal is delivered and verified**, not when
the code around it got better. The goal is what the user asked for; under the workflow it is the
work-doc's Goal line (the workflow skill, Plan step 2), written at Plan and unchanged until the
user changes it.

**Never chase what you find on the way.** A pre-existing bug, a failing check, a law break in a
file you happened to open, dead code, a missing test, a smell, a refactor that is obviously right:
write it down the moment you see it, one line with its `file:line`, and go straight back to the
goal. It is not investigated, fixed or refactored in this task; it gets a task of its own, and the
user says when. This holds however small or cheap the fix looks, because a two-minute detour costs
two minutes off the goal plus every minute the verify, the review and the sweep then spend on
ground the plan never claimed, and because one detour is how the next ten start. A follow-up with no
`file:line` and no one-line statement of what is wrong is not a follow-up, it is a feeling. They go
under `## Follow-ups` in the work-doc when the workflow runs, in the closing report when it does
not, and into the release notes printed at the close, where the user says what happens next.

**A serious find is told at once, and still not fixed.** A security hole, data loss, a money error
or a live outage found on the way goes to the user in one line the moment it is seen, so the risk
is never sitting unread in a list; it is fixed in this task only if they say so.

**A check that was already red is not this task's.** Run it at the base commit; if it was red
there, file it as a follow-up and judge the change on everything else. It still stops a deploy: a
red check on the commit being shipped fails the first of the six proofs (1.11), so the user is told
and its fix becomes a task of its own, never a detour inside this one.

**Scouts and reviews tag what they find.** Every scout row and review finding is `introduced` or
`present at base`, checked against the base commit. Only an `introduced` one is this task's; a row
`present at base` is disposed as `follow-up, present at base`.

**The two things fixed on the way, and nothing else**, because the goal is not delivered without them:

1. **What your own diff broke, orphaned or got wrong.** Your change's leftovers are your change (1.1), and a Critical finding of the review against this diff is this diff's own defect.
2. **A true blocker**, a defect the goal cannot be delivered or verified around. Say in one line whether it blocks delivery or verification, fix the smallest thing that unblocks it, record it in the task's Log line as a change the plan did not authorize so the review sees it, then get back on the goal.

**Not reasons to fix something on the way:** "it serves the goal", "it is related", "it is cheap",
"it was right there", "it cuts tokens or drift", "while I'm here". Each is how a chase starts.

**The drift check, at every phase boundary and after every task.** One line: the goal, and whether
the work since the last boundary served it. Work that did not is named, stopped and moved into the
follow-ups. Drift caught at the review costs the whole review.

Where the follow-ups land: `## Follow-ups` in the work-doc (the workflow skill, Plan) when the
workflow runs, the closing report when it does not, and the release notes printed at the close
(the workflow skill, Verify & Deploy step 7), which is where the user sees the list and says what
happens next.
