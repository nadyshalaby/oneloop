# 1.6 [rule] The four principles (long form)

> **Long form.** The binding text is the short form in `law/engineering-code.md`, which
> the oneloop code-rules hook hands to the session with the first code file it reads or edits. This file keeps the reasons and the full
> wording the short form compresses; read it when a rule needs its reasoning. If the two ever
> differ, the short form wins and this file is the defect.

**Think Before Coding.** The first move on any non-trivial prompt is not a keystroke, it is a question. State your assumptions out loud. List at least two plausible interpretations when the ask is ambiguous; commit to one and say why. Push back when the request collides with a cap, a prior decision or evidence already on screen. Stop and ask when the next step depends on a fact you do not have; never substitute a guess. Re-read the scope line and its note before the first edit. The loop's Scope step is where truth is collected: the map, the file, its direct callers and imports, read this session, and the note's line on what could go wrong. *The test: can you point at the line in the scope note, the file or the user's message that authorized this code? If not, stop.*

**Simplicity First.** Ship the minimum code that solves the stated problem. Build only what was asked; speculative features, "while I'm here" extras and unrequested options are out. No abstraction for single-use code. No error handling for scenarios the call site's contract makes impossible. No configuration knobs for hypothetical tuning. Prefer deletion over addition. *The test: if you removed this line, would the request still be met and the checks still pass? If yes, the line is overhead.*

**Surgical Changes.** Every changed line traces to the request. Touch only the files the scope line names; a file outside it is the scope ratchet's business: stop, restate the scope, wait for the yes. Do not refactor adjacent code "while you're in there"; that is another task. Match the surrounding style even when you would have written it differently. Note pre-existing smells or bugs in the side finds; never silently rewrite them. Clean up every orphan your own diff created, in the task. Dead code already in a file you touched is a follow-up with its `file:line`, never a hunk of this diff (1.9): the list goes to the user, who says when it goes. *The test: can a reader trace every hunk back to the request and the scope line? If not, the diff is too wide.*

**Goal-Driven Execution.** Convert every imperative ask into a verifiable goal: the loop's checks first (lint, typecheck, the tests, `ui_check` on UI paths), then the exact command, grep or assertion that proves the behaviour. Prefer machine-checkable verifications; a look at the screen is for genuine UI-shape changes, which is what `ui_check` is. When a verification fails, stop and report; never loosen the check to make it pass. *The test: can you name the exact check that flips from red to green when it is done? If not, it is not yet a goal.*

Section 14.1 carries seven worked examples of these principles being broken; cite it by example number when one applies.

_Adapted from Andrej Karpathy's observations on the recurring failure modes of large language models asked to write production code._
