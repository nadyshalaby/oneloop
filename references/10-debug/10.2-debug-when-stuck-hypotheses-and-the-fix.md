# 10.2 [protocol] Debug when stuck: hypotheses and the fix

Read in debug mode, after 10.1's D1: a 4-phase scientific method, and 10.1 holds D1 and the
triggers. Do not skip phases. Do not let urgency push you into "just try X".

**The hypothesis chain and the root cause are written in this session.** The workflow sends
only its three helpers (the workflow skill, Helpers), and none of them plans, so the chain is
written here: the hypotheses ranked most likely first, each with the experiment that would kill
it and the exact command. **Running the experiments, judging what they printed, choosing the
fix and writing it stay in this session too**, and the fix itself is an Implement task (the
workflow skill, Implement).

**The advisor weighs the root cause twice more** (5.7), whenever the tool list holds one: before
D4, with the confirmed hypothesis and the experiment that confirmed it, and at the circuit
breaker, before the halt is written. The halt still goes to the user. What the advisor says
about the code is a hypothesis like any other, and D3 is how it is tested.

### D2, pattern analysis

If the codebase has a working analogue, this phase is gold. If not, skip to D3.

1. **Find a working similar example:** another endpoint, service or form in the same module that
   does something analogous and works, or a different feature that uses the same library or
   pattern correctly.
2. **Read the working example COMPLETELY,** end to end, not skimmed: imports; setup (constructor,
   init, dependencies); the exact API call shape; error handling; type signatures; any subtle
   difference in how it's wired up.
3. **List every difference between working and broken,** exhaustively, including what
   "shouldn't matter": a different env var, config option, dependency version, middleware order
   or schema reference. A difference you dismiss as "shouldn't matter" is often the cause.

### D3, hypothesis and test (scientific method)

1. **Write down ONE hypothesis,** verbatim, in the work-doc:

   > **Hypothesis 1.** I think `<X>` is the root cause because `<Y>` (evidence: `<Z>`).

   If you can't articulate it cleanly, you don't have a hypothesis yet: go back to D1.
2. **Make the smallest possible change:** ONE change, ONE variable. Do not bundle "fix X and also
   clean up Y."
3. **Run, observe:** did the failing test pass? Did all other tests stay green? Does the manual
   reproduction now work?
4. **Outcome.** Yes → D4, implemented properly with a test. No → revert your change and form a
   new hypothesis; do NOT pile on more fixes. Update the work-doc:

   > **Hypothesis 1.** Disproved. The change to `<X>` had no effect on the failure.
   > **Hypothesis 2.** ...

**Circuit breaker: STOP after 3 hypotheses.** If 3 fail, stop and surface to the user: this is no
longer a failed hypothesis, it's an architectural problem, and each fix revealing a new problem
in a different place is the strongest possible signal. In the work-doc:

> **Halt.** 3 hypotheses tested, all disproved. The architecture appears wrong, not the code. Surfacing for discussion.

Then a one-paragraph summary: what you tried, what you learned, what you suspect the
architectural issue is. Do not attempt fix #4.

### D4, implement the fix properly

The hypothesis is confirmed. Don't ship the experimental change as-is:

1. **Specify the failing regression test.** It fails before the fix (so you know it tests the
   right thing), passes after, is the smallest reproduction possible, and covers the **source**
   of the bug, not just the symptom. Write it now, before the fix, and watch it fail for the
   right reason. Paste the red.
2. **Apply the fix at the source:** ONE change, the root cause, not the symptom. If you patched
   at the symptom site during D3 to confirm the hypothesis, **revert that** and apply the real
   fix at the source. The fix stays inside the task's declared files; a root cause in a file the
   plan did not name is a scope change: say so, add the file to the Plan with a task, then fix it
   there. **The mode is `test-authoring`, with the fix's order: the failing regression test
   first, then the fix that turns it green** (9.2). The same hands write both halves in the same
   task; that is the seam a regression test exists to close.
3. **Verify:** the new failing test passes, all existing tests still pass, the manual
   reproduction no longer reproduces.
4. **Return to Implement or Verify.** Update the work-doc: `status: implement` (continue with the
   remaining tasks) or `status: verify` (this was the last task); the task's Log line carries the
   root cause in one line, the hypothesis chain (compressed) and the regression test. Tick the
   task's Plan box with its proof line; the work carries on in Implement (the workflow skill,
   Loop-back).

### Forbidden patterns

These are the rationalizations that turn a 30-minute bug into a 3-hour bug. Catch yourself:

| Thought | Reality |
|---|---|
| "Quick fix for now, investigate later" | "Later" never comes. The symptom fix masks the source. |
| "Just try changing X and see if it works" | That's not a hypothesis, that's gambling. |
| "Add multiple changes, run tests" | If it passes you don't know which change worked. |
| "Skip the test, I'll manually verify" | Then you have nothing protecting against regression. |
| "It's probably X, let me just fix that" | "Probably" → write down the hypothesis first. |
| "One more fix attempt" (after 2+) | The circuit breaker exists for a reason. |
| "Each fix reveals a new problem" | Architectural issue. Stop and escalate. |

### Working example (for orientation)

> **Bug.** `<test runner command> test/integration/invitations.test.<ext>` fails with `expected 200 to equal 401`. The first attempt added `await` to the auth header parsing. Didn't help.
>
> **D1.** Stack trace points to the auth middleware. Added log at boundary: middleware sees a `Cookie: better-auth.session=…` header, returns 200. But test expects 401. Oh, the test calls a route that **does not** require auth. So the actual issue is the route handler itself returning 200 with no body, but the test asserts a specific JSON shape and the assertion library reports it as 401.
>
> **D2.** Compared with another integration test that works. Difference: that test sets `Accept: application/json`. Hmm, the HTTP framework's default response is plain text without it.
>
> **D3.** Hypothesis: missing `Accept: application/json` causes the framework to return non-JSON, which the test's `.body` parser then misinterprets as auth-required. Set the header. Test passes.
>
> **D4.** Wrote a regression test (new test name: `invitations endpoint returns JSON regardless of Accept header`). Watched it fail. Fixed by setting `c.json(…)` explicitly in the route (which forces content-type) instead of relying on the test sending `Accept`. Watched it pass. All other tests still green.

The forbidden version of the same bug:

> Tries adding `await`. Doesn't work. Tries adding error handling. Doesn't work. Tries upgrading the framework. Doesn't work. Now in a refactor of the whole middleware stack, 2 hours later, still failing.
