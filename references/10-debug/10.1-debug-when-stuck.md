# 10.1 [protocol] Debug when stuck

## Debug when stuck: the root cause

Two ways in. **Stuck:** 2 honest fix attempts on the same task made no progress, or any trigger
below fired. This is the workflow skill's stuck-twice rule (Implement) in full, and it adds no
ledger item: the work-doc's `status` stays `implement`, and the hypothesis chain is written in
chat under `<task>, debugging` and ends up compressed in the task's Log line. **A bug fix at
Plan** runs D1 below before any task is drafted (the workflow skill, Plan step 3), by reading
only, since nothing runs before the user's yes (the `explain` skill): Step 1 in full and Step
4, the bad value traced through the code; Step 2's reproduction and Step 3's boundary logging
wait for the logic gate's yes. Random fixes waste time and create new bugs. **Always find the
root cause before attempting a fix. Symptom fixes are failure.**

**The advisor weighs the root cause before a fix rests on it** (5.7), whenever the tool list
holds one: first as debugging opens, with the symptom and the evidence on the page; its two
later moments are in 10.2. What it says about the code is a hypothesis like any other.

### Trigger conditions

Switch into debug mode when ANY of the following:

- ≥2 failed fix attempts on the same task in Implement
- A test failure whose error message contradicts the Plan section's expectation
- An unrelated test fails after your change (sign of unexpected coupling)
- Reproducing the bug requires steps that are not deterministic (intermittent)
- A user reports the feature doesn't work after you marked it done (a regression after the close)

### D1, root cause investigation (BEFORE any fix)

1. **Read the error carefully:** the full stack trace, not just the top line; the exact error
   code, file path and line number; what changed recently (`git log --oneline -20`,
   `git diff HEAD~5..HEAD <touched files>`).
2. **Reproduce reliably:** the exact steps; does it fail every time, sometimes, once? An
   intermittent failure does not go on to D3 until it is deterministic, since intermittent
   reproductions hide race conditions, ordering issues and leaked state: add logging at component
   boundaries until you can predict the failure.
3. **Gather evidence at component boundaries.** In a multi-component system (request → service →
   repo → DB; client → axios → server → HTTP framework → service → DB), log what data enters and
   exits EACH boundary, run the failing scenario once, and note the boundary where the data goes
   wrong; now you know which component fails, so analyze just that one and don't guess upstream.
   In a layered backend the boundaries are: the tenant-resolution middleware, request-body
   validation (fails here: a validation issue), transaction or tenant-DB setup (a pool,
   search_path or config issue), the ORM query (query construction), the result mapping (a type
   mismatch), the response. Temporary logging is allowed only within what the user permitted
   (6.10, Q4), and every line of it is removed before Verify & Deploy and proven gone in the
   cleanup sweep.
4. **Trace the bad value backward:** where is it used, where does it come from (a function
   argument, a DB query, the environment), who called that with the bad value, where did that
   come from, until the originating point. Fix at the origin, not where the bad value was
   observed.

**In debug mode, D1 is not the end:** read 10.2 (pattern analysis, one hypothesis at a time, the
circuit breaker, the fix with its regression test) before the next edit. It is four phases, and
none is skipped.
