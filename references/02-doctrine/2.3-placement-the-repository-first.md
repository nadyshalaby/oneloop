# 2.3 [law] Placement: the repository first

Read before any source or test file or folder is created (the code rules; the workflow skill,
Implement step 1). Where a file lives and what it is called is a contract: the repository's own
where it has one, and 2.2 where it has none. A structure already in the code outranks the one
written in 2.2, because consistency inside one codebase is worth more than agreement with any
outside standard.

1. **Detect.** Before writing a file, look at where its siblings live. Read any `CLAUDE.md`,
   `AGENTS.md`, `README`, `ARCHITECTURE.md` or `CONTRIBUTING.md` that documents a layout. Look
   at the two or three most recently added files of the same kind.
2. **State it.** Write the detected convention down in one or two lines before you create
   anything: *"services live at `src/<domain>/<domain>.service.ts`, types flat beside them in
   `<domain>.types.ts`, tests beside the file they test."* An undetected convention is one you
   are about to break.
3. **Obey it exactly.** Every new file matches it: not approximately, not "close enough", not
   "the newer style I prefer". If the repo keeps its types flat beside the service, yours goes
   flat beside the service, even though 2.2 would have put it in `types/`.
4. **A gap reads 2.2.** Where the repo has made no decision (a new repository, or a kind of file
   it has never had, so step 1 finds no sibling of that kind), read 2.2 in full before creating
   the file: its structure is the decision, and you say that you are making it.
5. **Never migrate as a side effect.** Moving existing files to match anything is its own task
   with its own approval; a feature that also relocates twelve files is a diff nobody can
   review. Note the drift, finish the feature, offer the migration.

**Two layouts in one repository is the failure this order exists to prevent.** A new convention
introduced beside an old one does not replace it; it doubles the places a reader has to look,
permanently.
