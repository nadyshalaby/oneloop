# 5.7 [reference] The advisor, a second opinion at every decision

**A decision made alone, by the context that wants it to be right, is the cheapest place for a
task to go wrong.** Where the session has an advisor tool, every strategic decision goes past
it before it is taken. The rule is 1.4; this file is when the call is made, how it
is set up, what happens to the answer, and what happens when there is no advisor at all. Read
it at task start, with the workflow skill's ledger when the workflow runs, and follow it on
every route.

## What it is, and how you know it is there

The advisor tool (1.4) is a second model the user chose, at least as
capable as the one running. On Claude Code it is the `advisor` tool: it takes no input, reads
the whole conversation with every tool call and result, and returns guidance. The user picks
it (`/advisor`, the `advisorModel` setting or `--advisor`), and the runtime attaches it only
where it accepts the pairing with the model that is running.

**The test is the tool list, and nothing else.** An `advisor` in your tools means consult it;
none means decide alone. Never infer it from the model's name, from a settings file or from
what an earlier task saw: the strongest model gets a second opinion exactly as the smallest
one does, whenever the tool is there. Presence is per context, too. This session may hold the
tool while a helper on another model does not, or the other way round, which is why
every context looks at its own list.

**Record it once, at task start, on the ledger's first print** (the workflow skill, the
ledger): `Advisor: yes.` or `Advisor: no.`; outside the workflow, one line in chat the first
time a decision comes up. It can change mid-task, because the user can switch the model or
the advisor. When the tool appears or goes, say so in one line and follow the tool list from
then on.

## At the prompt boundary, on Claude Code

This setup wires `hooks/advisor-cue.sh` to `UserPromptSubmit`, the event that fires on every
prompt and takes no matcher. It prints one line into the turn: the logic-first gate (1.4) and
the moments to consult the advisor; the rest of the rule is the always-on law's. **It judges
nothing and refuses nothing.** A hook cannot see a tool list, so it can neither know whether
an advisor is there nor tell a decision from a greeting; making it refuse would block work
over a guess. What it buys is reach: the rule arrives in a session that never loaded this
skill, and in every turn after a compaction. The cue is the rule speaking, exactly as the
edit guard's refusal is 1.1 speaking.

**It is kept short on purpose, and its fixture test caps it.** Something printed into every
prompt of every session is paid for in every one of them, so the cue carries only the
logic-first gate and the trigger list; the always-on law carries the rest, and the detail
lives here, where it is read once.

## The run points

One call per run point, made before the decision, never after it to bless it.

| Run point | Where | What the advisor weighs |
|---|---|---|
| Before the question batch goes out | the workflow skill, Plan step 5 | the goal line, the batch, and the recommended option of every question |
| Before the plan is committed to | Plan step 7, after the lane | the Done-when checks, the tasks and their order, the lane, what is left out |
| Before a change of direction while building | Implement, a re-plan or a loop-back | the scope change, the re-cut, the fork the plan left open |
| Before a confirmed root cause becomes a fix, and before a halt | Implement, stuck twice (`10.2`) | the evidence, the hypothesis, the experiment that confirmed it |
| Before the review's findings are decided | Verify & Deploy step 3 | the keeps, the refutations and the deferrals |
| Before the landing executes, and before a deploy | Verify & Deploy step 6 | the landing, the six proofs (1.11) |
| Before the work is called done | Verify & Deploy step 7, the self-audit | the filled self-audit, the Evidence lines and what the checks did not reach |

**Between run points, four more moments, on every route and outside any phase:**

- **Before any recommendation goes to the user.** Every `AskUserQuestion` puts a recommended
  option first (1.4); the ranking is a decision, and it is weighed before the user sees it.
- **Before a change of direction**: a re-plan, a loop-back, an approach dropped for another.
- **When the same failure has beaten you twice**, which is also when the edits stop for the
  root cause (10.1).
- **Before anything hard to undo**: a deploy, a flag flip or a live config change (1.11), a
  migration, a deletion, a history rewrite the user asked for by name.

The other routes (16.1, 16.2, 16.3, 16.13 and 15.19) have no phases of their own to carry a
run point. The four moments above are the whole rule there: an audit's verdict, a triage
decision, a brainstorm recommendation and a design direction are each a recommendation to the
user.

## How the call is set up

The advisor takes no input, so the question is whatever the conversation says just before
the call. Write it down first, in a line or two: **the decision, the options on the table,
the one you lean to, and the evidence behind it.** Then call. A call made with nothing stated
gets advice about nothing in particular, at the price of a full read of the conversation.

## What happens to the answer

**The advisor advises. It never decides, and it never proves.**

- **A report, never proof** (1.5). What it claims about the code is re-derived here,
  this session, before anything rests on it.
- **Evidence outranks it.** Where its advice and your own fresh evidence disagree, say the
  clash in one line and run the check that settles it. Never follow it past a red, and never
  drop your evidence because a stronger model sounded sure.
- **The user, the goal and this law outrank it.** Advice that contradicts the user's
  words, moves the goal (the work-doc's Goal line) or lowers a cap, a ban, a check or a gate
  is not taken. Say the clash in one line; when it is the user's to settle, it goes through
  `AskUserQuestion`.
- **It never replaces the user.** A decision that is theirs is still asked. The advisor
  shapes which option goes first, and the option text may say what it said.
- **It never replaces a helper.** It has read this whole conversation, so it holds
  most of this session's reasons for believing what it believes; the reviewer is sent
  precisely because it holds none (`agents/er-reviewer.md`).
- **It can decline.** Record `advisor: declined` and decide alone, as below.

**The record rides the tick.** The reflection that closes a run point carries what the call
did, in a few words: `advisor: agreed`, `advisor: moved the schema task first`, `advisor:
declined`, or `advisor: none`. In the workflow that line lands in the work-doc with the tick
(the workflow skill, the ledger). A run point passed with the tool in the list and no call
made is a false tick, and 1.5 governs false ticks.

## The helpers

A helper may hold an advisor of its own, attached to its model and reading its own
conversation. The two that decide something carry the advisor line in their own file
(`agents/`): `er-builder` consults before it settles an approach, `er-reviewer` before it
settles a verdict, and both before they return; each report ends `advisor: <what it changed,
or agreed, or none>`. `er-reader` decides nothing and carries no such line.

## When there is no advisor

Say so once, on the record line, and carry on. **The step does not drop out; only the call
does.** State the decision, the options and the evidence exactly as you would have before a
call, then decide. Never fake a consultation, never write `advisor: agreed` for a call that
was not made, and never make the user's choice of model or advisor a condition of working.
When they ask why it is missing, one line is enough: on Claude Code the advisor must be at
least as capable as the model that is running, and a pairing the runtime rejects is never
attached, so the tool simply is not in the list.

## What it is not for

- **A fact one command would settle** (1.10). Run the command.
- **Every thought.** One call per run point; each call re-reads the whole conversation at the
  advisor's price.
- **Re-opening what the user decided.** Their answer stands; it is not a draft.
- **Blessing unverified work.** *"The advisor agreed"* is not an Evidence line.

## Anti-rationalizations

| Thought | Reality |
|---|---|
| "I am already the strongest model, it has nothing to add." | The test is the tool list. The user paid for a second opinion; the strongest model alone is still one context that wants to be right. |
| "It is a small decision." | The run points are the list, and size is not on it. |
| "No advisor here, so the step is skipped." | Only the call drops out. The decision is still stated with its options and its evidence. |
| "The advisor agreed, so it is proven." | A report, never proof. Run the check (1.5). |
| "The advisor said X and the user said Y." | The user wins. Say the clash in one line. |
| "I will write `advisor: agreed`, it would have." | A false tick, and 1.5 governs it. |
| "The reviewer can be skipped, the advisor looked at it." | It read the diff with all of this session's reasons in view. Fresh eyes are the reviewer's, and the review still runs (the workflow skill, Verify & Deploy step 2). |
| "I will ask it which file holds the handler." | One grep settles that. The advisor is for decisions (1.10). |
| "The cue fired again, so I should call it again." | The cue is the rule, printed at the prompt boundary because a hook cannot see a decision. The run points decide when you call. |
