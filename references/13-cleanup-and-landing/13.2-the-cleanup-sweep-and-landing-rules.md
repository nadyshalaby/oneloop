# 13.2 [protocol] The cleanup sweep and the landing rules

The detail behind the workflow skill's Verify & Deploy steps 5 and 6: the cleanup sweep (Step D)
and the four rules every landing keeps. The release notes' format and voice are 16.13's.

---

## Step D. The cleanup sweep

Runs after the review's fix pass and before the landing. Thirteen classes, each producing a
one-line evidence record in the Evidence, zero counts included. **A defect this task created is
fixed inline; a defect that was already there is filed under Follow-ups with its `file:line` and
never fixed here** (1.9). Never silently left either way. Every fix here is a code change and
obeys 9.2 and the Plan's files.

**The scans run in this session**: the workflow sends only its three helpers, and none of
them runs commands for the sweep (the workflow skill, Helpers). One command,
`bash ~/.claude/engineering-rules/scripts/scout.sh --sweep <base> <work-doc>`, runs the scouts
(their rows serve classes 10 and 13, so they are not run again) and then `scripts/sweep.sh`,
which holds the patterns of the eight mechanical classes (1, 2, 3, 6, 7, 8, 12, 13), proves
each check on a planted hit first and prints every hit. Classes 4, 5, 9 and 11, and the rest of
10, run by hand as their rows say. Paste the raw output and exit status; this session judges
every line, decides fixed against follow-up, and makes every edit and every commit.

| # | Class | How to check | Remedy |
|---|---|---|---|
| 1 | Debug output added while working | The sweep | Remove; domain code logs through the project's logger (`clean.debug-artifact`). |
| 2 | Commented-out code, `// removed:` markers | The sweep, plus a read of every added comment block | Delete; git is the history. |
| 3 | Ownerless `TODO` / `FIXME` / `HACK` / `XXX` | The sweep (the owned shape the law scout uses, 9.5) | Add an owner or a ticket, or remove. |
| 4 | Dead code, both directions | For every symbol the diff added or exported, grep for a caller; for every call, import or reference the diff removed, grep for what is left of its target, a symbol, file, type, constant, fixture, flag, config key, env var or translation nothing references any more. The project's own dead-code tool first when it has one (knip, depcheck, ts-prune, vulture, deadcode, `cargo udeps`), over the touched scope; the grep covers strings, configs, templates and docs, not only imports, and proves it can find a planted reference before it reports a zero (1.5) | Delete, or wire it. |
| 5 | Unused imports, dependencies, env vars | The project's linter for imports; manifest vs `grep -rl` for deps; env schema vs usage | Remove, or use it. |
| 6 | Scratch files, fixtures, temp dirs, empty dirs | The sweep | Delete; `rmdir`. |
| 7 | Placeholder values and stub returns | The sweep | Replace or justify in writing; a seeded placeholder image survives only when the release notes name the slot as still needing a real asset (15.23). |
| 8 | Unrelated changes that snuck in | The sweep, against the files the Plan's tasks name | Justify (add the task retroactively, with the user's sign-off) or revert that path's changes. |
| 9 | Stale references | `grep -rnE '<old-path>\|<deleted-file>\|<renamed-symbol>' <docs, configs, the work-doc>` for every path or symbol this task moved, renamed or deleted; check every markdown anchor in touched docs still resolves | Update the reference. Never rewrite a historical record; fix the live file. |
| 10 | Pre-existing errors, law breaks and dead code in touched files | The triad scoped to touched files, plus the law scout (9.5) and, over touched UI files, the design scout (15.29), each finding labelled *introduced* vs *pre-existing* by diffing against `<base>`; class 4's method over every touched file for the dead code that predates the task | Introduced: already fixed in Implement or the fix pass. Pre-existing errors, law breaks and dead code: **listed as follow-ups with their `file:line`, never fixed here** (1.9); this task has one goal and a pre-existing defect is not it, so the list goes to the user at the close and they say which becomes the next task. A dead-code follow-up carries its zero-reference proof per symbol, and one that **looks dead but may not be** says so: an export on a package's public entry point or consumed by another repo; a name a framework finds by convention (a route file, a migration, a lifecycle hook, a decorator or annotation target, a serializer or ORM field); a symbol registered through reflection, a DI container or a string lookup; anything reached by a dynamic import or a string the grep could not resolve. Files outside the touched scope stay out; that is a codebase audit (16.3). |
| 11 | Leaked runtime state | `lsof -i :<port>` / `docker compose ps` / the process list, for every process Verify & Deploy started; `git status` for a `.env.local` or fixture staged into the diff | Tear it down; unstage it. |
| 12 | Dead branches created during the task | The sweep | `git branch -d` locally; remote deletion only with the user's confirmation. |
| 13 | Focused or skipped tests left on | The sweep, then the law scout's `test.focused` / `test.skipped` rows (9.5) | Remove the focus; a skip names a ticket or the test is fixed or deleted. |

Evidence record shape, one per class: *"Class 8 scope creep: 0 unrelated paths (27 paths, all
in the Plan's files)"*.

## The landing rules

The workflow skill's Verify & Deploy step 6 asks the landing when there is a choice. Whichever is
chosen, four rules hold:

- **Discard needs the typed word.** Throwing the work away takes the user typing the literal word
  `discard` in `AskUserQuestion`'s free-text answer; "yes", "delete it" or "go ahead" is not
  consent, so ask again. Deleting the branch is enough and stays recoverable through `git reflog`
  (never `git reset --hard`, `rm -rf` or `git clean`), and a pushed branch is deleted remotely
  only when the user confirms that too.
- **Tests again after a local merge.** Merging into the base branch on this machine: pull with
  `--ff-only` first, and after the merge `git status` is clean and the project's tests run green
  there before pushing.
- **The worktree goes last.** Remove a worktree (never when the branch is kept) only after the
  work-doc has moved to `docs/work/done/`, because the live doc sits inside the worktree until
  then; remove it from the project repo, not from inside it, and check with `git worktree list`.
  If removal fails over uncommitted changes, stop and ask; never `--force`.
- **Leave a worktree the way you entered it.** A session that entered through `EnterWorktree`
  leaves with `ExitWorktree` first.
