# 12.2 [reference] Review coverage

**Was every changed file read by something that could judge it?** Coverage is the guarantee;
how the reading is organised is not.

- **Every changed path is claimed.** Build the list once, at the start:
  `git diff --name-only <base>..<head> -- . ':(exclude)docs/work/*'`. Assign each path to every
  check whose surface it touches (most belong to two or more); a path you cannot confidently
  classify goes to the quality-and-plan check (12.7), so no file is left uncovered.
- **The quality-and-plan check is never narrowed.** It applies its semantic tier to every
  touched file and re-judges every law-scout row: it is the floor under every other economy.
- **Read wider than you judge.** The list bounds what you diff, not what you read: open the
  caller, the type or the guard a finding needs, and say in the finding why; never widen the
  diff itself.
- **An empty list is not a clean verdict.** A check with no paths is not run, and that is
  written down with the reason; zero findings over zero files is never counted as a verdict,
  and neither is a list the exclusion emptied.
- **`docs/work/` is excluded:** the work-doc is the ruler the diff is measured against, and the
  review writes into it while it runs. The quality-and-plan check still reads it in full as an
  input and flags any changed file no task authorized.
- **The coverage ledger** makes "every file was covered" checkable instead of asserted: one row
  per changed path, written at the start, its verdict filled once when the reports come back,
  about the bytes read on this round only.

```
| path                | checks read it                        | verdict    |
|---------------------|---------------------------------------|------------|
| src/auth/session.ts | security, quality-and-plan, coherence | clean      |
| src/ui/Button.tsx   | quality-and-plan, design conformance  | 2 findings |
```

- **One review, one challenge, one fix pass,** however much the fixes changed; the cap counts
  rounds, not checks. The rule is the workflow skill's (Verify & Deploy step 4): the fix gets
  the triad and the checks it touches and no second review, so a mistake the fix makes is
  caught only by those checks.
- **A silent check proves nothing.** A report that says "clean" without a ledger row behind
  each path is an assertion, and an assertion is what the review exists to replace.
