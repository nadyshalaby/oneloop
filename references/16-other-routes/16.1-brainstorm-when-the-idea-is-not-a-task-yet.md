# 16.1 [route] Brainstorm, when the idea is not a task yet

## Brainstorm (Socratic pre-task refinement)

A brainstorm is the front door for an idea that is not a task yet. It runs ONE Socratic conversation, 1 or 2 forking questions per turn, reflection before each following question, until the user signals intent to build. At that signal it writes a one-paragraph distillation and hands it to the loop (the always-on law), whose Scope step opens on it. Nothing is edited until the Scope step has the user's yes.

The law binds throughout the brainstorm: every question goes through `AskUserQuestion`, and nothing is edited.

---

### When to invoke

This route is picked by its command, `/oneloop:brainstorm`, or from prose when the user's most recent message contains any of the following (case-insensitive substring match):

- `shaping`
- `let's discuss`
- `let's think`
- `what if`
- `explore the idea`
- `what do you think`
- `considering`
- `thinking about`

A prompt typed after `/oneloop:brainstorm` is a brainstorm whatever verbs it carries. From prose, do NOT start a brainstorm when the user's message already contains build-intent verbs (`add`, `implement`, `build`, `fix`, `refactor`, `ship`, `make this happen`): those are plain requests, and a plain request runs the loop. A prompt can match both lists at once, and when it does the positive trigger wins: the build-verb block applies only to a prompt that carries none of the trigger phrases above, which is why `let's discuss adding rate limiting` starts a brainstorm and `add rate limiting at 100 req/min per IP` does not. A brainstorm is strictly pre-task; it is not a discussion step that runs after the scope line has been printed.

---

### How it runs

A brainstorm runs an interactive Socratic loop until the user signals build intent. The loop has exactly three rules. Violating any rule is a failure of the route.

**Rule 1, 1 or 2 questions per turn. Never more.** A brainstorm is NOT the Scope step's one pick-list. The Scope step asks at most one batched pick-list per task, and only what the code cannot answer (the law, 1.4); a brainstorm asks 1 or 2 questions to surface a real fork in the user's thinking. Each question still goes through `AskUserQuestion`, like every question in this law (1.4): one call, one or two questions, the fork's branches as the options with the strongest first, and the free-text input the tool adds serving as the open answer. What makes a brainstorm different from the Scope step is the count and the purpose, not the delivery.

**Rule 2. Every question must surface a real fork.** A real fork is a choice where the two branches lead to different builds, different checks, or different user experiences. Vanity questions ("what do you want to call this?", "what color theme?") are forbidden here; the code, or the Scope step's one pick-list, settles those after graduation. If you cannot name the fork the question opens, do not ask it.

**Rule 3. Reflect before asking the following question.** Each turn begins with one sentence (≤25 words) that mirrors back what the user just said in their own framing. Then the following 1-2 questions. The reflection proves you read what they wrote and gives them a chance to correct a misread cheaply.

**Anti-loop guard.** If you have asked 3 or more questions in a row without the user offering new substantive information (their answers shrink to one-word affirmations, or they ask you for an opinion), surface the implicit graduation offer verbatim: *"Want me to write up what we have so far and scope it as a task?"* If they say yes, graduate. If they decline, change tactic, propose a concrete option instead of asking another open-ended question.

**No file, during the brainstorm or at graduation.** The conversation transcript IS the state. Do NOT create a scratch path of any kind. Nothing is written until the loop's Edit step, after the Scope step has the yes; a brainstorm never edits.

---

### Graduation rule

Graduation fires when the user signals intent to build. The signal phrases (case-insensitive substring match against the user's most recent message) are:

- `let's build`
- `let's do this`
- `OK make this happen` (and the case variant `make this happen`)
- An explicit task-shaped ask of the form "now add `<feature>`" / "now implement `<change>`" / "now fix `<bug>`"

`ship it` is deliberately NOT a graduation signal: it reads as a request to commit and deploy what exists, and a brainstorm has built nothing yet. A user who meant "start building" says so with one of the phrases above. Do not add it back.

**A graduation signal is not the Scope step.** The loop still prints the scope line and the note before anything is edited (the law), then proceeds: no yes is waited for.

On graduation, execute these three steps in order. Do not reorder. Do not skip.

**Step 1. Distill.** Write a one-paragraph distillation (≤120 words) of what the brainstorm clarified. The paragraph names: the user's underlying goal, the chosen approach (the surviving fork branch), the constraints surfaced during the conversation, and any explicit non-goals. The distillation is for whoever picks the work up next, and it must be self-contained enough that someone who did not see the brainstorm can read it alone and understand the locked decisions. The four elements map straight onto the Scope step: the goal and the approach become the scope line's files and the note's first line (what changes), the non-goals what the note leaves out, and each constraint a line of what could go wrong.

**Step 2. Print the distillation.** Print it in the handoff turn under a `## Brainstorm distillation` heading, the four elements labelled, so the Scope step opens on it instead of restating a one-line goal from scratch. It stays in the transcript; no file is written.

**Step 3. Hand off.** End the brainstorm turn with a single explicit handoff line: *"Brainstorm done, handing off to the loop. The distillation is above."* Then run the loop's Scope step (the law): read the map, find the files, print the scope line and the note, proceed. The handoff is the terminal action of the brainstorm.

### Anti-rationalizations

These thoughts mean STOP and apply the listed reality.

| Thought | Reality |
|---|---|
| "I'll just start editing now since we have enough" | Nothing is edited before the Scope step's scope line (the law). A brainstorm never edits. |
| "The user said let's build, so the scope is approved" | A graduation signal is not the Scope step. The loop prints the scope line and the note, then proceeds (the law). |
| "This idea stayed small, so I'll skip the scope line and just build it" | Size changes nothing. Every task, from a typo to a new module, runs the same loop. |
| "The user said something vaguely build-shaped, that's a graduation signal" | Graduation signals are the explicit phrase list in the Graduation rule. Vague build-shape is not on the list. Ask one more reflecting question instead. |
| "I'll ask 8 questions in one turn to save time" | Rule 1 caps at 2 questions per turn. Batched questions kill the Socratic reflection loop. |
| "A brainstorm can run *after* the scope line if they want more discovery" | A brainstorm is strictly pre-task. Once the scope line is printed, the discovery channel is the Scope step's one pick-list. Re-entering a brainstorm mid-task is forbidden. |
| "I'll write a quick scratch file to track ideas" | No scratch files. The transcript is the state; nothing is written before the Edit step. |
| "The user asked me 3 questions back-to-back, I'll just answer and keep brainstorming" | The anti-loop guard fired. Surface the verbatim graduation offer: *"Want me to write up what we have so far and scope it as a task?"* |
| "I'll ask a vanity question to keep the conversation warm" | Every question must surface a real fork. If you cannot name the fork, do not ask the question. Propose a concrete option instead. |

### Where the pieces are

The Socratic loop and the graduation rule are this file. The scope line, the note, the explanation and everything after are the loop's (the always-on law).

### One-line summary

Reflect → ask 1-2 forking questions → loop until the user signals build → distill → print the distillation and hand off to the loop, whose Scope step prints the scope line and the note and proceeds.
