# 16.1 [route] Brainstorm, when the idea is not a task yet

## Brainstorm (Socratic pre-task refinement)

A brainstorm is the workflow's front door for an idea that is not a task yet. It runs ONE Socratic conversation, 1 or 2 forking questions per turn, reflection before each following question, until the user signals intent to build. At that signal it writes a one-paragraph distillation and hands it to the workflow (`/engineering-rules:workflow`), whose Plan opens on it (the workflow skill, Plan). Nothing is written to disk until Plan's logic gate has the user's yes (Plan step 8).

The law binds throughout the brainstorm: every question goes through `AskUserQuestion`, and nothing is edited.

---

### When to invoke

This route is picked by its command, `/engineering-rules:brainstorm`, or, inside the workflow, by its route table (the workflow skill, Routes and references) when the user's most recent prompt contains any of the following (case-insensitive substring match):

- `shaping`
- `let's discuss`
- `let's think`
- `what if`
- `explore the idea`
- `what do you think`
- `considering`
- `thinking about`

A prompt typed after `/engineering-rules:brainstorm` is a brainstorm whatever verbs it carries. From prose, do NOT start a brainstorm when the user prompt already contains build-intent verbs (`add`, `implement`, `build`, `fix`, `refactor`, `ship`, `make this happen`): those go straight to the workflow, the default route. A prompt can match both lists at once, and when it does the positive trigger wins: the build-verb block applies only to a prompt that carries none of the trigger phrases above, which is why `let's discuss adding rate limiting` starts a brainstorm and `add rate limiting at 100 req/min per IP` does not. A brainstorm is strictly pre-task; it is not a discussion step that runs after Plan has started.

---

### How it runs

A brainstorm runs an interactive Socratic loop until the user signals build intent. The loop has exactly three rules. Violating any rule is a workflow failure.

**Rule 1, 1 or 2 questions per turn. Never more.** A brainstorm is NOT Plan's question round. Plan batches questions to settle requirements (the workflow skill, Plan step 5); a brainstorm asks 1 or 2 questions to surface a real fork in the user's thinking. Each question still goes through `AskUserQuestion`, like every question in this law (1.4): one call, one or two questions, the fork's branches as the options with the strongest first, and the free-text input the tool adds serving as the open answer. What makes a brainstorm different from Plan is the count and the purpose, not the delivery.

**Rule 2. Every question must surface a real fork.** A real fork is a choice where the two branches lead to different builds, different Done-when checks, or different user experiences. Vanity questions ("what do you want to call this?", "what color theme?") are forbidden here; those go to Plan's question round after graduation. If you cannot name the fork the question opens, do not ask it.

**Rule 3. Reflect before asking the following question.** Each turn begins with one sentence (≤25 words) that mirrors back what the user just said in their own framing. Then the following 1-2 questions. The reflection proves you read what they wrote and gives them a chance to correct a misread cheaply.

**Anti-loop guard.** If you have asked 3 or more questions in a row without the user offering new substantive information (their answers shrink to one-word affirmations, or they ask you for an opinion), surface the implicit graduation offer verbatim: *"Want me to write up what we have so far as a draft plan?"* If they say yes, graduate. If they decline, change tactic, propose a concrete option instead of asking another open-ended question.

**No work-doc, during the brainstorm or at graduation.** The conversation transcript IS the state. Do NOT create `docs/work/.brainstorm-scratch.md`, `docs/work/.brainstorm-<slug>.md`, or any scratch path. The work-doc is Plan's, written once after its logic gate has the user's yes (the workflow skill, Plan step 8); a brainstorm never writes it.

---

### Graduation rule

Graduation fires when the user signals intent to build. The signal phrases (case-insensitive substring match against the user's most recent message) are:

- `let's build`
- `let's do this`
- `OK make this happen` (and the case variant `make this happen`)
- An explicit task-shaped ask of the form "now add `<feature>`" / "now implement `<change>`" / "now fix `<bug>`"

`ship it` is deliberately NOT a graduation signal. The handover question (6.4, Q4) recommends the unreviewed straight-to-main option only when the user's prompt carries that literal phrase, and a brainstorm hands off in the same turn to a Plan that may run that same question, so a user who meant "start building" would be steered into a merge nobody read. Do not add it back.

**A graduation signal is not the logic gate's yes.** Plan still shows the logic with the `explain` skill and asks through `AskUserQuestion` before anything is written (law 1.4).

On graduation, execute these three steps in order. Do not reorder. Do not skip.

**Step 1. Distill.** Write a one-paragraph distillation (≤120 words) of what the brainstorm clarified. The paragraph names: the user's underlying goal, the chosen approach (the surviving fork branch), the constraints surfaced during the conversation, and any explicit non-goals. The distillation is for whoever picks the work up next, and it must be self-contained enough that someone who did not see the brainstorm can read it alone and understand the locked decisions. The four elements map straight onto Plan (the workflow skill): the goal and the approach become the Goal line's who it is for and what changes (step 2), the non-goals its what is left out, and each constraint a must-not-change Done-when check (step 6).

**Step 2. Print the distillation.** Print it in the handoff turn under a `## Brainstorm distillation` heading, the four elements labelled, so Plan opens on it instead of restating a one-line goal from scratch. It stays in the transcript; no file is written.

**Step 3. Hand off.** End the brainstorm turn with a single explicit handoff line: *"Brainstorm done, handing off to the workflow's Plan. The distillation is above."* Then begin the workflow's Plan from its step 1 (the workflow skill), which prints the ledger and opens its first item; the brainstorm never does either. The handoff is the terminal action of the brainstorm.

### Anti-rationalizations

These thoughts mean STOP and apply the listed reality.

| Thought | Reality |
|---|---|
| "I'll just create the work-doc now since we have enough" | The work-doc is Plan's, written after its logic gate's yes (the workflow skill, Plan step 8). A file written mid-brainstorm forks state between transcript and disk. |
| "The user said let's build, so the logic is confirmed" | A graduation signal is not the logic gate's yes. Plan shows the logic with the `explain` skill and asks (law 1.4). |
| "This idea stayed small, so I'll skip Plan and just build it" | Size is not a routing signal. A brainstorm hands off to Plan like every other build ask; Plan's lane (step 7) is where a small task gets lighter, on checkable facts. |
| "The user said something vaguely build-shaped, that's a graduation signal" | Graduation signals are the explicit phrase list in the Graduation rule. Vague build-shape is not on the list. Ask one more reflecting question instead. |
| "I'll ask 8 questions in one turn to save time" | Rule 1 caps at 2 questions per turn. Batched questions kill the Socratic reflection loop. |
| "A brainstorm can run *after* Plan starts if they want more discovery" | A brainstorm is strictly pre-task. Once Plan runs, the discovery channel is its question round. Re-entering a brainstorm mid-flow is forbidden. |
| "I'll write a quick scratch file at `docs/work/.brainstorm-<slug>.md` to track ideas" | No scratch files. The transcript is the state until Plan writes the one work-doc. |
| "The user asked me 3 questions back-to-back, I'll just answer and keep brainstorming" | The anti-loop guard fired. Surface the verbatim graduation offer: *"Want me to write up what we have so far as a draft plan?"* |
| "I'll ask a vanity question to keep the conversation warm" | Every question must surface a real fork. If you cannot name the fork, do not ask the question. Propose a concrete option instead. |

---

### Where the pieces are

The Socratic loop and the graduation rule are this file. Routing is the workflow skill's route table; the goal line, the Done-when checks, the logic gate, the ledger and the work-doc are the workflow skill's Plan.

---

### One-line summary

Reflect → ask 1-2 forking questions → loop until the user signals build → distill → print the distillation and hand off to the workflow's Plan, which asks the logic gate and then writes the work-doc.
