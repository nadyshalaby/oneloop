# 9.1 [phase] Phase 3, Implement

**Build it in ordered stages, each one proven, scanned and committed before the next
begins.** Read 9.2 (implement and test), 9.3 (the checklist), 2.1, 2.2 and 14.1 before the
first line. Read the catalog domains your task touches (3.1, 3.2, 3.3) as you reach them.

**Each stage is built by a builder agent** (5.5), a fresh `general-purpose` agent on `sonnet`,
sent the builder prompt pasted whole with its file allowlist, its acceptance criterion, the
repo brief, the test mode (9.2) and the anchor's North-Star Goal and top Non-Goal. Stages
whose allowlists are disjoint go out in one message so they run at once, with
`isolation: "worktree"` when their trees would collide. This is a mandatory send (1.8); with
agents off (4.4) the stage is built here inside the same allowlist. **The ledger, the scouts,
the triad, the commit and every tick stay in this session**, and what a builder returns is
proven here before anything ticks. A builder that reports a defect outside its allowlist has
filed a follow-up, not a fix (1.9).

## The order, and why it is fixed

| Stage | What lands | Why here |
|---|---|---|
| **1 Foundation** | Every file more than one later task writes: shared types, schema changes, constants, config, new module skeletons. No business logic. | A file edited from two places later is a conflict, whether the two edits are an hour or a second apart. Landing them once, first, removes the whole class. |
| **2 Modules** | The features themselves, one coherent piece of work at a time, in dependency order. | A piece that depends on another's contract goes second, and builds against the contract the plan wrote. |
| **3 Assembly** | Wiring: routes registered, handlers subscribed, components mounted, containers composed. Then **boot the system.** | Nothing before this proves the parts fit. A system that compiles and does not start is not a system. |
| **4 Testing** | The tests for everything the round landed, each with a watched failure and a named mutation (9.2). | A test written after the code, and proven to fail when the code is broken, tests the code. |

**Two exceptions to "tests last", both mandatory.** A **bug fix** writes the failing
reproduction first, in the module stage, watches it fail for the right reason, then fixes it;
that is what proves the fix fixes the bug. A **refactor with no safety net** (6.8, Q4 = A)
writes its characterization tests first, as its own foundation task. Everything else tests in
stage 4. The test mode per task is recorded in Daily Updates (9.2).

**A stage that does not apply is listed with a reason, never dropped.** A two-file change
has no foundation stage and says so; a docs-only change has no assembly boot and says so.
**Boot is mandatory** whenever the diff touches anything the application loads at startup.

**One commit closes each stage that landed files**, on the task branch, never one per task,
never a partial task. Never commit on the default branch: when you are on it, create
`<type>/<slug>` first and say so. The commit format is in 9.2.

## Per task, every time

a. **Open the task in the doc first.** Mark it in progress in the Sprint Backlog before the
   first edit, and take it in the backlog's order; several run at once only when the plan
   runs them as parallel stages, and then they are the next ones (7.3).
b. **Read before you write.** Open every file the task touches, in full, and the closest
   existing example of the same kind of thing. Match its conventions.
c. **Place before you create.** Every new file's path and name follows section 2.2 and the
   plan's allowlist. A file the plan did not name is a scope change: stop, say so, and get
   it added to the backlog before writing it.
d. **Write the minimum that satisfies the task**: the minimum that meets the acceptance
   criterion with its edge cases handled (empty, one, many, absent, malformed, duplicate,
   unauthorized, the error path), not the minimum that compiles.
e. **Prove it, right there.** Run the narrowest real check that can fail: the test, the
   typecheck, the command. Paste the real output.
f. **Tick and write together.** The checkbox and the Daily Updates entry land in the same
   edit, as the task closes. No catch-up writes.
g. **Reflect in one line.** What changed, whether it passed, what is next.

## At the end of every stage

1. **Run the scouts** (9.4, 9.5, and the design scout 15.29 when the stage wrote a UI file)
   over the files this stage wrote, through a fork that reads the scout files, runs them
   over the stage's paths and returns the staging tables with every row `staged` (5.5). A
   fork runs on this session's model by construction and takes no `model` (1.8). This is a
   mandatory send (1.8): the stage does not tick without it, and skipping it is an
   `agent skipped: <reason>` on the item with one of the three reasons 1.8 allows; with
   agents off (4.4) the scout files are read from disk and run here, over the same paths,
   with the same tables. With agents on, the files stay out of this context, and the
   dispositions stay in it either way. Coverage line first. Fix the trivial in-scope candidates now
   and mark them `fixed`; `stage` the rest; every candidate gets exactly one disposition.
   Paste every table into Daily Updates; a stage that wrote no UI file records
   `design scout: no UI file in scope` instead of a third table.
2. **Sweep the stage's leftovers, both directions**, over the stage's own diff: classes 1 to
   5 and 9 of 13.1 (debug output; commented-out code and `// removed:` markers; ownerless
   markers; dead code; unused imports, dependencies and env vars; stale references). Dead
   code here runs both ways: every symbol the stage added has a caller, and every symbol
   whose last caller, import or reference the stage removed is deleted with it, along with
   the types, constants, fixtures, flags, config keys, env vars, translations and doc lines
   that served only it. One evidence line per class with a count, zero included; a leftover
   found is fixed in the stage, never carried to the finish. Then the reuse line: for every
   symbol the stage added, the search that found no existing equivalent, pasted (1.1); a
   search that finds one sends the stage back to reuse it.
3. **Re-run the triad** over the touched scope. Red sends you back into the stage.
4. **Boot**, at the assembly stage and whenever the stage touched startup config.
5. **Write the stage's entry** into Daily Updates: what landed, what was proven, what did
   not, the scout tables, the sweep lines, the reuse searches, the commit.
6. **Commit the stage**, explicit paths, no attribution.
7. **Remove the dead code that was already in the files this stage touched, in its own
   commit.** Over every file the stage touched, list each symbol, export, registration,
   file, flag, config key or env var with zero references across the repo, by class 4's
   method in 13.2 (the project's own dead-code tool first when it has one; a grep that covers
   strings, configs, templates and docs and proves it can find a planted reference, 1.5),
   with the proof per symbol. Delete them, re-run the triad, and commit as
   `chore(<scope>): remove dead code in touched files`, separate from the stage commit so a
   veto is one `git revert`. What 13.2 class 10 lists as looks-dead-but-may-not-be is offered
   through the wizard tool instead of deleted. A stage that finds none records
   `dead code in touched files: 0` and makes no commit. Name the commit and every symbol in
   the stage's entry; the update log (16.13) carries them to the user.
8. **Re-print the ledger** with a one-line reflection naming the stage.

## When something does not fit

- **A defect in code this task did not plan to touch:** write it down as a follow-up with
  its `file:line` and one line saying what is wrong, and keep building (1.9). The one
  exception is a defect that genuinely blocks this task: say in one line why it blocks, fix
  the smallest thing that unblocks it, and name it in Daily Updates as a change the plan did
  not authorize, so the review sees it. *"It was right there"* is not a block.
- **A task you cannot finish:** stop at it. Keep everything already on disk. Report which
  tasks landed and which did not. Do not half-land a task to keep a tick. The ledger item
  stays open.
- **Stuck twice on the same symptom:** stop implementing, insert the Phase 3b item, and go
  to 10.1. A third guess is not a plan.
- **An approach that feels grand:** open 14.1 and find the matching example before
  committing to it.
- **A change of direction:** a scope change, a stage the plan has to be re-cut around, a
  loop-back, a fork the plan left open. Before you take it, the advisor (5.7), whenever the
  tool list holds one. A fork that is the user's to settle still goes to the user, through
  the wizard tool, with the advisor's view behind the option that goes first.

## Never destroy working-tree state

The git safety law in `SKILL.md` 1.7 binds here above all: never `git checkout -- <path>`,
`git restore`, `git stash`, `git reset --hard` or `git clean`. Restore a mutated line by
editing it back. Copy a file if you need a backup.
