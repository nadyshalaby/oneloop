# 7.1 [phase] Phase 2, Plan

*Full mode only. Quick mode restates its approach in chat at the end of Phase 1 (6.1,
step 6) and goes straight to implementation.*

**The plan comes from a planner agent, and the planner writes the work-doc** (5.5). At this
phase it is a fresh `general-purpose` agent on `opus`, sent the planner prompt pasted whole
with the ask, the clarify answers, the anchor, the repo brief, the coverage map, the base
commit and the one path it may write. It creates `docs/work/<YYYY-MM-DD>-<slug>.md` from the
template (7.2) and fills it: the approach with its rejected alternatives, the stages in
execution order with their contended resources, a file allowlist and a test mode per stage,
the acceptance criteria as checkable lines, and the risks. That is the point of the send. The
context that decided how the work is cut is the context that writes the cut down, on the
model the decision is worth and with eyes that never sat through the clarify round, instead
of dictating it to the session that did. This is a mandatory send (1.8): the phase does not
tick without it, and the only exits are the three reasons 1.8 names; with agents off (4.4)
the same plan is written here, against the same files.

**What stays in this session: the read-back, the publish, the ledger, saying the plan out loud,
and every edit to the doc after the planner's.** A plan is a proposal even when it arrives as
a file, and the transcription that used to force you to read it is gone. Step 2 is what
replaces it, and it is not optional: an agent's output is a report, never proof (1.8).

**Full mode no longer stops for a sign-off.** The plan is written, checked, published and
said in chat, and then the work starts. Nothing waits on an answer, because a plan the user
has to approve before anything moves is a stop that buys less than the spec review (8.1)
right behind it. What still goes to the user is a genuine fork: a decision the planner
brought back as a question, an ambiguity nobody settled in Phase 1, or anything that moves
the anchor. That is one question through the wizard, asked the moment it appears, never a
ceremonial gate at the end of the phase.

## Step 1. Send the planner

Brief it with, in this order: the ask in the user's own words, every clarify question and the
answer it got, the anchor (5.2) in full, the repo brief (6.13), the coverage map (6.15), the
base commit, the absolute path of 7.1, 7.2, 2.2 and 9.2, the existing files the work will
touch, and the one path it may write: `docs/work/<YYYY-MM-DD>-<slug>.md`, today's date and a
`kebab-case` slug of six words or fewer. Say outright that this path is the only thing it may
write. When shaping (16.1) already created that file, name it and say so: the planner edits
it in place, and its frontmatter, its `## 0. Phase ledger` and its `## Shaping Provenance`
block survive untouched.

## Step 2. Read what came back, against the repository

The doc is not the plan until this session has read it. Run these in order, and fix every
`no` here, yourself, before anything else happens:

1. `git status --porcelain`. Exactly one path differs from the run before the send, and it is
   the work-doc. A second path is a finding against the whole send (5.5): revert it, say so,
   and treat what the planner claimed with the suspicion the breach earns.
2. The file is at the path you named, and it is the only live doc under `docs/work/` (7.3).
3. It is at the template's shape (7.2, current-shape conformance): section 0 first with its
   ten items and Phase 2 the single in-progress one, the section labels in the skeleton's
   order, and every frontmatter key carrying a value from the field reference.
4. The ask, the anchor and the Q&A came through verbatim. You hold the originals. Compare
   them; do not skim them.
5. Every citation resolves. Open each `file:line` the approach leans on. A plan that cites a
   line which is not there was written from a summary of the repository (1.5).
6. Every acceptance criterion has a covering task, every task names the files it may write
   and carries its `→ verify:` line, and every path named either exists or is a new file
   whose placement 2.2 allows.
7. The plan serves the anchor and nothing else. A stage that serves a Non-Goal comes out here
   and goes to `## Follow-ups` (1.9).

## What the doc says when it is right

The headings are the template's own (7.2), spelled its way, in this order. Three of them carry
no number, which is exactly what a list of "sections 1 to 9" gets wrong, and a renumbered
heading breaks every citation the rest of the law makes to it.

| Heading | What is in it when Phase 2 closes |
|---|---|
| `## 0. Phase ledger` | the ten items, Phase 1 ticked, Phase 2 the single one in progress |
| `## 1. Original ask` | the user's words, verbatim, not summarized |
| `## Primary Goal & Guardrails` | the anchor locked in Phase 1, all five parts. No number, by design |
| `## 2. Clarifying Q&A` | every question asked and the answer it got |
| `## 3. Acceptance Criteria` | observable, checkable statements. Each one gets a task |
| `## 4. Approach` | the design, the layering, the files it touches, the alternatives rejected with the reason, the `### Repo Brief` (6.13) and the `### Execution stages` block |
| `## 5. Sprint Backlog` | the tasks, each with the files it may write and its verify line |
| `## 6. Daily Updates` | empty until Phase 3 |
| `## 7. Sprint Review (Phase 4 / 5)` | empty until Phase 4 |
| `## 8. Retrospective` | empty until Phase 6 |
| `## Follow-ups` | empty until something is found that the goal does not need (1.9) |
| `## Law self-audit` | empty until Phase 6 Step F |
| `## Update log` | empty until Phase 6 Step F |

On the shaping path (16.1), `## Shaping Provenance` sits between section 0 and section 1, and
nowhere else.

## Rules the plan itself must obey

- **Every acceptance criterion has at least one covering task.** A criterion with no task
  is a criterion nobody will meet.
- **Every task names the files it may write.** Placement is decided here, against section
  2.2, not discovered while implementing. Every new file's path and name is written down.
- **Every task names how it will be proven**, as `→ verify: <one-line check>`.
- **Every task is one commit's worth of work**, five to thirty minutes, and lists production
  files only; test authoring is the testing stage's own task.
- **Order the tasks into stages** (9.1): foundation first for every file two later tasks
  both write, then modules in dependency order, then assembly, then testing.
- **The plan cites, it does not assert.** Any claim about how the code behaves today comes
  with a `file:line`.
- **A UI-bearing task names the design spec** it builds against, or names authoring one as
  its first deliverable (15.1), states the read and the dials (15.20), and carries the
  composition plan (15.22) in its Approach when the surface is a marketing page.

## Step 3. Publish the page

Where the runtime can publish a page, the first publish happens here, on the doc as the
planner left it and your read-back corrected it, and the returned link is written into
frontmatter `page_url` and said once in chat (7.3), before any code is written. When shaping already published it, read
`page_url` back and confirm it instead of publishing again: the file is published once on
either path and never twice on that one. Publishing is this session's, never the planner's.

## Step 4. Worktree, when Phase 1 chose one

When the workspace question (6.4, Q2) chose a separate copy, create it now, before the gate,
so the work starts in a workspace that already exists. Quick mode runs this same
procedure at the close of Phase 1.

```
# Path priority: an existing .worktrees/ dir, then an existing worktrees/ dir, then a
# CLAUDE.md override, then ask. Default: .worktrees/<slug> at the repo root.
git check-ignore -q .worktrees || { echo '.worktrees/' >> .gitignore; git add .gitignore; git commit -m 'chore: ignore .worktrees'; }
WORKTREE_PATH="$(git rev-parse --show-toplevel)/.worktrees/<slug>"
git worktree add "$WORKTREE_PATH" -b "<type>/<slug>"
cd "$WORKTREE_PATH"
<package manager install command>      # from the repo brief, never guessed
<project test command>                 # once, for a clean baseline; paste the result line
```

On Claude Code, where the repository has no worktree convention of its own, the `EnterWorktree`
tool (or `claude --worktree <slug>` at launch) does the same job: it creates the worktree under
`.claude/worktrees/<slug>`, copies in the files a `.worktreeinclude` names, and `ExitWorktree`
leaves it. Record its path and branch the same way. The block above stays the procedure for
every other runtime and for a repository that already keeps its worktrees elsewhere.

Write the path, relative to the repo root, into frontmatter `worktree`, and the branch into
`branch`. Every later command in the task runs inside the worktree. Never create a worktree
without the ignore check; an un-ignored `.worktrees/` pollutes the user's status forever.

## Step 5. Say what you are about to build

Tell the user, in chat, in plain words and in under ten lines: what you are going to build,
the acceptance criteria, the approach in a few lines, what you are deliberately not doing,
the path and the link to the doc, and that the work starts now. This is a statement, not a
question, and nothing waits on it: they read it while the spec review runs, and one word from
them turns the plan around at a cost the whole design is built to keep low.

A decision the planner brought back as a question is different, and it does not travel in
this block. Ask it on its own, through the wizard tool, before the work that depends on it:
one question, the strongest option first, and the answer written into the work-doc's
Clarifying Q&A. The same holds for anything that would move the anchor (5.2), in this phase
or any later one.
