# 7.3 [reference] Work-doc rules

Read this file at Phase 2 step 3, where the first publish happens, at every stage of Phase 3,
because the gate below binds every code edit, and at Phase 6 Step F, where the last publish
does.

## The work-doc is the single record, and the page is the doc

Where the runtime can publish a page (on Claude Code, the `Artifact` tool), publish **the
work-doc itself**, exactly as it stands on disk, and nothing else. There is no rendered
report, no HTML template, no payload, no second representation. If something is worth
publishing, write it into the work-doc and the page gets it for free.

- **No extra file in the shipped tree.** Publishing writes nothing into `docs/work/`.
- **Never publish the archived copy under `docs/work/done/`.** A different path mints a
  different link, and the one the user already holds goes stale.

## When it publishes

1. **First publish, Phase 2 step 3**, on the doc the planner wrote once the read-back has
   corrected it (7.1) and before the gate, so the user reads the plan they are approving on
   the same link they keep for the whole task. The publish is the session's on every path;
   a planner writes the file and never publishes it.
2. **Republish on every phase-ledger tick.** Same beat as the edit plus re-print the ledger
   already mandates: edit `## 0. Phase ledger`, save, republish, print. It is not a new step.
3. **Final republish at Phase 6 Step F**, riding the one closing edit that ticks 6c and 6d
   and writes `status: done`, and happening **before** the `git mv`.

## One link for the life of the task

- **The first publish writes the returned URL into frontmatter `page_url`**, and every
  republish targets that URL. Resume reads the frontmatter, so that field is the only thing
  carrying the link across a lost session; a resume with `page_url` still `null` after a
  first publish mints a second link, which is the defect this rule prevents.
- **Say the link out loud once**, in chat, when it is first created.
- **After that, say it again only when the user asks or when it changes.** A link that never
  moves is the proof the design worked.

## Quick mode

Quick keeps nothing in the project tree. Its page, where the runtime can publish one, is a
scratch markdown file assembled from the blocks quick already prints: the anchor, the ledger
block, the repo brief (6.13), the Evidence Ledger rows, the coverage ledger and decision table, the
self-audit and the update log (16.13). Publish when that file first exists, republish on every
ledger tick, one stable link for the run, said once.

**Give it a fresh private directory per run with `$(mktemp -d)`, never a fixed name in the
shared temp directory.** A predictable path in a world-writable directory is one another
user can pre-fill with a symlink; `mktemp -d` picks an unguessable name and creates the
directory mode `0700`. **Nothing quick publishes lands in `docs/work/`.**

## Project-relative paths only

The page goes to whoever the user sends it to, and everything in the doc travels with it.
Write every path project-relative, from the first time you write it: `docs/work/<slug>.md`,
never the same path with somebody's home directory in front of it. The frequent offenders:
frontmatter `worktree`, the repo brief's commands, the Sprint Backlog's file allowlists, the
Evidence Ledger's commands, the Daily Updates' file names. A section missing from that list
is not exempt.

## Secrets on a page that travels

Personal handles, tokens, credentials and customer data follow the path rule, more sharply: a
doc that is also a page is no place for any of them. Keep them out from the first time you
write the line. **Nothing screens the page for you.** The law scout's secret patterns (9.5)
run over the touched scope, never over the work-doc, and a publish hands the file to the
runtime unread. A published page is private until somebody shares it, which is what keeps
this a discipline rather than an incident, and it is also why the discipline has to hold.

## Never load-bearing

Publishing is an enhancement. **No phase may hard-require it.**

- **Publishing is never a precondition for closing any ledger row.** 6d's exit artifact is
  the printed self-audit and update log plus the work-doc on disk.
- **A runtime with no publish tool says so once, in one line, then carries on**: `No
  page-publishing tool in this runtime, so the work-doc stays a file on disk, at <path>.`
- **Do not go silent about it.** Silence about a missing tool reads like silence about a
  skipped step.

## The update log is unchanged by any of this

The five field headings stay exactly as they are, in this order: **Problem**, **Root
cause**, **Solution**, **Verification evidence**, **Deployment status**. The log prints to
chat, block by block, and is appended under `## Update log` by the closing edit (13.2).

## The work-doc is the map, and the gate that holds it

**In full mode the work-doc is the only map, and the work follows it** (`SKILL.md` 1.4, 1.9).
Not your memory of the plan, not the message that started the task, not a better order that
occurred to you while building. The doc says which phase is open and which task is next, and
that is the phase and the task.

- **The phase the ledger shows open is the phase you are in.** Code lands in Phase 3, in
  Phase 3b, in the Phase 5 fix pass and in the Phase 6 cleanup. In any other phase, an edit
  to a code file means the ledger is wrong or the edit is: fix whichever it is, in the doc
  first.
- **The task the Sprint Backlog lists next is the task you take**, in the backlog's order,
  marked `- [>]` while it runs. Parallel stages may run several at once (5.5), and then they
  are the next ones: a task may not start while an earlier one still waits. Doing a later
  task first is not efficiency; it is a plan nobody approved, and the review has no way to
  trace it.
- **A reorder is an edit to the doc, with its reason.** Move the task in the backlog, say in
  one line in Daily Updates why the order changed, then build. The order may change; the
  silence about it may not.
- **Every tick is written as it lands.** A ticked task with nothing under Daily Updates is a
  claim with no record behind it (1.4), and the next session reading the doc is told the work
  was done and shown nothing.
- **A task has exactly one live work-doc.** A second one under `docs/work/` means an earlier
  task never closed; archive it under `done/` before building anything else.

**The gate, on Claude Code.** This plugin's `work-doc-gate.sh` hook holds that line at the
tool boundary: while a live work-doc exists under `docs/work/`, an edit to a code or test
file is refused when the doc disagrees with it, and the refusal names which of the rules
above it broke. Prose and generated files are never gated, so the work-doc itself, the README
and every document stay editable at any moment, which is what makes the gate escapable the
honest way: **bring the doc up to date and the edit goes through.** A task with no live
work-doc, which is quick mode, a trivial ask or a repository that keeps none, is not gated at
all. Routing an edit around the gate through the shell is the move 1.1 forbids for the edit
guard, and it is forbidden here for the same reason: the hook is this law speaking, not an
obstacle.
